## Decisions worth reviewing

1. **Split `views/gio_follow.py` → + `views/member_binding.py`.** The single file came out at 239
   lines, over the 200-line rule in `docs/code-standards.md`. Split by concern (binding vs. follow
   resolution), same precedent as `views/person.py` / `views/person_list.py`. This is one file more
   than the phase plan listed; no collision risk (parallel agent owns none of `views/`).
2. **Two extra selectors** beyond the four specced: `member_binding(clan_id, user_id)`
   (`select_related('person')` — `selectors.clan.member_by_user_id` joins `user`, not `person`) and
   `person_claimed_by_other(person_id, user_id)`. Both are ORM reads that would otherwise sit
   inline in a view, which the Layering rule forbids.
3. **`GET gio-follows` lists ancestors ∪ own-override rows**, not every deceased person in the
   clan. Three `source` values only exist for those; listing the whole clan would need a fourth
   ("not following") and would duplicate `lich-gio`. Response also carries `followed` (the resolved
   answer) and `bound` (false ⇒ client should prompt for `toi-la`).
4. **`source` precedence:** `override False` → `da-bo`; else ancestor → `truc-he`; else
   `thu-cong`. A redundant `enabled=True` on an ancestor reports `truc-he` — lineage is the
   truthful explanation.
5. **`PUT gio-follows/{pid}` rejects a person without BOTH lunar day and month** (400). Otherwise
   the row would be stored and silently never fire.
6. **404 vs 400 split.** Ids from the URL path that miss → 404 (`gio-follows/{person_id}`); ids
   from a request body that miss → 400 (`toi-la` body `person_id`, incl. cross-clan and
   soft-deleted). Cross-clan is 400 per the plan.
7. **`toi-la` claimed-person check is double.** `person_claimed_by_other()` for the civil 400, plus
   `except IntegrityError` around the save for the race. Never a 500.
8. **`POST /devices` returns 201 on create / 200 on update**, body `{platform, is_active}` — the
   token is never echoed. `DELETE` is 204 unconditionally (filtered by `request.user`), so the
   response reveals nothing about token ownership.
9. **Migration split as specced.** 0004 = the `ClanMember.person` column alone (additive, nullable,
   no backfill, `RemoveField`-reversible). 0005 = 3 tables + `Clan.gio_remind_before_days`,
   depends on 0004, drops independently. Both generated by `makemigrations` then split by hand, so
   the field defs are byte-identical to what Django derives.

## Unresolved questions

1. `GET /gio-follows` drops the `truncated` flag that `deceased_with_lunar_death` returns. At the
   5.000-person cap a clan could have its tail silently cut. Add it to the response, or is the cap
   far enough away not to matter for a preferences screen?
2. `PUT /gio-follows/{pid}` accepts a *soft-deleted* person? No — `get_person_or_none` filters
   `is_deleted=False`, so it 404s. But an existing override on a person who is later soft-deleted
   stays in the table and vanishes from `GET` (the person is not in `rows`). Correct per the plan
   ("nằm im vô hại"), but the user gets no signal that a followed person disappeared.
3. `toi-la` `_is_deceased` treats ANY death marker as deceased, which is wider than the
   `lich-gio` rule (needs day AND month). Deliberate, but it means a person with only
   `death_lunar_month` set can never be claimed and never appears in a calendar — a data-entry
   dead end that phase 8/9 may want to surface.
4. `Clan.gio_remind_before_days` has no API to change it (admin only). Phase 9's clan settings
   endpoint should expose it, or the default 3 is permanent for every họ.
5. `DELETE /devices` deletes the row rather than setting `is_active=False`, so the audit trail of a
   logged-out device is gone. Fine for MVP; flag if push-delivery forensics are ever wanted.
